This user reviews agent work through visual HTML pages instead of long chat text, using these skills: /suwagent:visual-spec (what and why), /suwagent:visual-plan (how), /suwagent:visual-recap (what was built and how it works), /suwagent:visual-deviation (only where the implementation departs from the spec, and why), /suwagent:visual-qa (a test guide for a tester), /suwagent:visual-guardrails (whether every acceptance criterion of a spec is guarded on the gate by a check that fails when the behaviour breaks) and /suwagent:agent-review (a diff-level code review by a separate reviewer, as a page). The pages are saved under docs/visual/<spec|plan|recap|deviation|qa|guardrails|review>/ and, by default, also published as claude.ai artifacts, whose links are recorded in docs/visual/<kind>/claude-artifacts.md.

The user's method, spec-driven with guardrails. The agent follows it in every repository that uses the plugin, greenfield or brownfield:

1. Size first. Every task that is not obviously tiny starts with /suwagent:task-triage: S (a bug or a change with no behaviour visible to a user or an API caller: a ticket and a test, no spec), M (the behaviour of an existing feature changes: a delta in that feature's living spec), L (a new feature or a change of a contract on the boundary: a spec and a plan). The agent proposes the tier, the user confirms in one word. The threshold is one question: does it change behaviour someone can see, or a contract?
2. One living spec per feature, never one per task or per repository. A feature is one behaviour with one owner. A task edits the feature's spec in place (criteria added, changed, dropped), with no changelog; after the merge the spec is rewritten as if the accepted deviations had been there from the start, and that final spec is what gets committed. The spec says what and why, never how; decisions are one sentence in the spec, or a file in docs/adr/ only when they span several features. A spec never lists its consumers.
3. Acceptance criteria are the contract between spec and code. Each has an id (AC-<feature>-<n>), and outside the spec it lives only as a guardrail naming that id: a test, a lint rule, a type check. The gate's rule is one-way: every criterion must have a guardrail, and every id in a guardrail must exist in this repository's spec; a test without an id is fine (a regression test, a bug test, a test adapting the app to another repository's contract). A criterion no automated check can prove is reworded or dropped, never left unguarded.
4. Boundaries between repositories are contracts, not shared specs. A feature used by many apps has one spec at its owner; the apps are tied to it by the generated contract (an openapi.json, an event schema), which the owner's CI compares with the main branch and fails on a breaking change. An app that adapts to a new contract version writes tests tagged with the contract's name and version (contract name@version), not with an AC id; it gets a delta in its own spec only when its own behaviour changes.
5. The gate is the only proof. One script, two modes: --quick in the hook after every turn of the agent, with a hard time budget of about 20 seconds, and the full gate before pushing and in CI, identical. The agent never edits the gate, the hooks, the lint configs or recorded behaviour (characterization tests); it asks the owner. A skipped step is a failure in CI. A rule the agent is told about goes as low as it can: a type, then a lint rule, then a test, then a hook; a sentence in AGENTS.md only for what none of these can check.
6. Review has two paths, and on both the human reads the spec and the guardrails page, never the test code. /suwagent:review-triage says which path: ordinary (the human reads the spec, the guardrails page and the recap; a separate reviewer agent reads the diff through /suwagent:agent-review) or careful (the human also reads the diff), taken when the change touches the always-careful list: login and permissions, payments, data migrations, code without characterization tests. The guardrails page and the review page are written by an agent that did not write the code, are valid until the merge request closes, and stay out of git.
7. Brownfield: the order is reversed. Before an agent changes legacy code it gets four things: AGENTS.md as a map (about 100 lines, links deeper), CONTEXT.md in the modules about to be touched (what the module is for, its traps, where to start; written by an agent, corrected by someone who knows the code), characterization tests around that code recorded before any change (they record today's behaviour without judging it; the agent never edits a recording, it fixes the code), and the gate script. Only then specs, and only for what is being changed: the spec never describes the whole legacy system. New things grow as separate projects in the same solution, one per group of features, with a boundary enforced by an architecture test or analyzer, not as folders in existing projects and not as microservices; legacy reaches a module only through an adapter. Greenfield: start from the owner's template, which already has the gate, the hooks and criteria.json.

The working agreement for larger changes (a new feature, several files, a change of behaviour, an API or data shape, or a choice between approaches):
- Before planning, offer in one line to write a visual spec (or a delta in the existing one), unless the requirements are already pinned down or an approved spec exists.
- Before writing code, offer a visual plan, and start implementing only after the user approves it.
- After the work is finished and verified, offer a visual recap. When a spec exists and the user wants only the differences rather than the whole story, or a record to keep next to the spec, offer /suwagent:visual-deviation instead: a short page with each departure from the spec, its reason and a keep / fix / decide recommendation.
- Before a spec'd feature is merged, offer /suwagent:visual-guardrails in one line; when the user asks whether criteria are covered or whether a test really guards, run it. It answers two separate questions, and both matter: is each criterion addressed by a guardrail on the gate, and would that guardrail fail if the behaviour broke. A test that touches the code path without asserting the criterion's result is not a good guardrail.
- When a change is ready for review, offer /suwagent:review-triage and, on the ordinary path, /suwagent:agent-review.
- When finished work goes to a tester, QA or the client's acceptance testing, offer /suwagent:visual-qa: a test guide without technical detail, written for the environment the user names (the agent asks for it if it isn't known).
- When the user declines one of these for a task, don't offer it again for that task.

What goes into git: only the final spec. Plans, recaps, deviation, QA, guardrails and review pages are working pages of one task and are gitignored (docs/visual/plan/, docs/visual/recap/, docs/visual/deviation/, docs/visual/qa/, docs/visual/guardrails/, docs/visual/review/ in .gitignore). When the agent writes one of these pages in a repository whose .gitignore doesn't cover them yet (check with `git check-ignore`), it recommends adding those lines in one line, and adds them only when the user agrees; after a no, it doesn't ask again in that repository.

When the user asks for a better, nicer or more visual README, recommend /suwagent:visual-readme in one line; start it only when the user asks for it. It redraws the README as light/dark pictures from a board page in docs/visual/board/.

Small or obvious changes (a typo, a one-line fix, a single well-specified function, a question) need none of these; the user expects them to be done directly.

The plugin also has ways of working for larger tasks. The user wants the agent to recommend the one that fits, in one line with a reason, when a larger task starts or its plan is approved. The agent starts autopilot, orchestrate, mr-chain, visual-readme and update only when the user explicitly asks for one of them (by its name, as in "użyj efficient-frontier", or in plain words); then it invokes the skill itself instead of asking the user to type the command. Otherwise it only names the command:
- /suwagent:autopilot when the user will leave the agent alone with the task ("idę spać", "zrób to beze mnie", "nie pytaj"), or the task is long and its decisions are routine. It works without questions, logs its decisions and ends with a visual recap.
- /suwagent:orchestrate (alias /suwagent:efficient-frontier) when the task is mostly volume: wide reading of the codebase, many files with mechanical edits, long test runs or logs. The main model decides while cheaper subagents do the volume.
- /suwagent:mr-chain when the feature is too large for one reviewable MR and should be delivered as stacked MRs, each built on the previous one. It splits the work, names the branches (e.g. SR-108-01-…) and keeps every change on the earliest branch that has its code. It builds the whole chain first and tests only on the last branch, fixing each failure in the MR that owns the code and merging it down. When the work is already on such a chain, the agent follows its rules without being asked.
- Both can apply: autopilot for autonomy, orchestrate for cost.
- plan-judge applies by itself when two or more plans exist for the same task. The agent uses it instead of choosing silently.
- limit-guard runs inside autopilot and orchestrate; it needs no recommendation.
- For an ordinary interactive task, the agent recommends nothing and just works.
The same rule applies as for the documents: after a no, the agent doesn't recommend a mode again for that task.
