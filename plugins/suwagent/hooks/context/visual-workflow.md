This user reviews agent work through visual HTML pages instead of long chat text: /suwagent:visual-spec (what and why), /suwagent:visual-plan (how), /suwagent:visual-recap (what was built and how it works), /suwagent:visual-deviation (only where the build departs from the spec, with a keep / fix / decide recommendation), /suwagent:visual-qa (a test guide for a tester, for the environment the user names; ask for it if unknown), /suwagent:visual-guardrails (is every acceptance criterion guarded on the gate by a check that would fail if the behaviour broke; a test that touches the path without asserting the result is not a guardrail) and /suwagent:agent-review (a diff-level review by a separate reviewer, as a page). Pages live in docs/visual/<spec|plan|recap|deviation|qa|guardrails|review>/ and are also published as claude.ai artifacts, recorded in docs/visual/<kind>/claude-artifacts.md.

The user's method, spec-driven with guardrails, is in the file named on the line above this text ("The method is described in …"): triage before anything (/suwagent:task-triage: S/M/L), one living spec per feature with deltas edited in place, criteria as guardrails with ids and a one-way gate rule, contracts on boundaries between repositories, the gate as the only proof, two review paths with an always-careful list, and in brownfield characterization tests and the gate before any spec. Read that file at the start of any task bigger than a one-liner and before writing a spec, plan, guardrails page or review; do not guess the method from this summary.

For larger changes (a new feature, several files, a change of behaviour, an API or data shape, a choice between approaches): offer in one line a visual spec (or a delta) before planning unless one is approved; a visual plan before code, and implement only after approval; a visual recap after verified work, or visual-deviation when only the differences matter; visual-guardrails before a spec'd feature is merged (run it when the user asks whether criteria are covered or a test really guards); /suwagent:review-triage and, on the ordinary path, /suwagent:agent-review when a change is ready for review; visual-qa when work goes to a tester or the client's acceptance. When the user declines one for a task, don't offer it again for that task. Small or obvious changes need none of these.

Git: only the final spec is committed. Plans, recaps, deviation, QA, guardrails and review pages are working pages of one task, gitignored (docs/visual/plan/, docs/visual/recap/, docs/visual/deviation/, docs/visual/qa/, docs/visual/guardrails/, docs/visual/review/). When the agent writes one in a repository whose .gitignore doesn't cover it (git check-ignore), it recommends the lines in one line and adds them only when the user agrees; after a no, it doesn't ask again there.

When the user asks for a better or more visual README, recommend /suwagent:visual-readme in one line (it redraws the README as light/dark pictures from a board page in docs/visual/board/); start it only when asked.

Ways of working for larger tasks, recommended in one line with a reason when a larger task starts or its plan is approved; autopilot, orchestrate, mr-chain, visual-readme and update are started only when the user asks for them by name or in plain words, and then the agent invokes the skill itself:
- /suwagent:autopilot when the user leaves the agent alone ("idę spać", "zrób to beze mnie", "nie pytaj") or the decisions are routine: no questions, decisions logged, a recap at the end.
- /suwagent:orchestrate (alias /suwagent:efficient-frontier) when the task is mostly volume: wide reading, many mechanical edits, long test runs; the main model decides, cheaper subagents do the volume.
- /suwagent:mr-chain when the feature is too large for one reviewable MR: stacked MRs (SR-108-01-…), every change on the earliest branch that has its code, the chain built first and tested on the last branch, fixes merged down; on a branch that is already in a chain, follow its rules unasked.
- Both can apply: autopilot for autonomy, orchestrate for cost. plan-judge applies by itself when two or more plans exist. limit-guard runs inside autopilot and orchestrate. For an ordinary interactive task, recommend nothing and just work; after a no, don't recommend a mode again for that task.
